# AR5 主从臂遥操 数据采集

**主臂 SO-101 带着从臂 AR5 走**，主臂手柄上的扳机控夹爪。这是 VEL 那一套，
不是 Vision Pro 那条路。

所有命令都在 **VEL 仓库根目录**下跑，不在这个文件夹：

```bash
cd ~/yuhang_workspace/算法/VEL/vel_ar5/openvla-energy
```

一条 episode = 一个 `.npz` + 每路相机一个 `.mp4`。

| 数组 | 形状 | 内容 |
|---|---|---|
| `state` | (T, 8) | 7 个关节角（rad）+ 夹爪开合（0~1，0 合拢） |
| `action` | (T, 7) | 末端位姿**增量** 6 维 + 夹爪开合 1 维 |
| `ee_pose` | (T, 6) | 末端绝对位姿，位置 m + 轴角 rad |

**动作空间是增量，不是绝对关节角。** 这和 servoJ 那条路不一样，两边的数据不能混在
同一个数据集里。但**转 DexGraspVLA 时两条路都能转** —— 关节角本来就在 `state` 里，
见第 7.2 节。

```
1 激活环境 → 2 查主臂 → 2.5 查夹爪 → 3 查相机 → 4 采集 → 5 回放+自动检查 → 6 删和编号 → 7 转数据集
```

## 2. 查主臂

```bash
python -m experiments.robot.ar5.probe_leader           # 扫口、ping 舵机
python -m experiments.robot.ar5.probe_leader --watch   # 实时看六个关节角
```

SO-101 是 6 个 Feetech STS3215，ID 1~6，走 `/dev/ttyACM0`，波特率 1000000。
用的是 `scservo_sdk`，不是 lerobot —— 装 lerobot 会动到这个环境配死的 torch。

**主臂全程不上力矩**，所以它一直可以徒手掰。程序每次启动都会查一遍，
有哪个舵机在锁力矩就警告。

关节怎么映射到 AR5：

| 主臂关节 | AR5 | 符号 |
|---|---|---|
| shoulder_pan | j0 | −1 |
| shoulder_lift | j1 | +1 |
| elbow_flex | j3 | +1 |
| wrist_flex | j5 | +1 |
| wrist_roll | j6 | −1 |
| —— | j2、j4 锁死不跟 | |

**夹爪的输入是 6 号舵机**，也就是手柄扳机。标定端点 −55.5°（合拢）到 +55.5°（全开），
归一化成 0~1。读不到扳机时按 **1.0 也就是全开**处理，不是合拢。

这说的是「操作员想让夹爪张多开」。真正把这个数变成夹爪动作的那一层，见下一节。

### 标定文件的两个坑

标定存在 `experiments/robot/ar5/joint_calibration.json`，由 `teleop_joint.py --save` 写。

* **`scale_overrides` 会盖过 `--relative`。** 存了缩放的那几个关节就不是 1:1 了，
  现在 `shoulder_pan` 1.0、`shoulder_lift` 0.617、`wrist_flex` 0.402。要看真实缩放
  就读启动时打印的 `scale` 那一列，别信注释。
* **`wrist_roll → j6` 的符号没验过。** 这个映射原来是给 j5 标的，换到 j6 之后符号
  还是老的。手腕转反了就 `--flip wrist_roll --save` 重存。

## 2.5 夹爪（末端硬件）

**型号 HKVR-TG9801**（航凯微电），三维触觉、柔性抓取的两指电动夹爪。

| 项目 | 参数 |
|---|---|
| 行程 | 0~98 mm |
| 单指夹持力 | 0~20 N |
| **打开 / 闭合时间** | **0.5 s / 1.6 s** |
| 位置重复精度 | 0.2 mm |
| 触觉传感器 | 1 个，**三维** |
| **通讯协议** | **RS 485** |
| 额定电压 / 最大电流 | 24 V / 1.5 A（额定 0.55 A） |
| 本体重量 / 推荐负载 | 400 g / 1500 g |

### SO101 + 夹爪接入（2026-09-22 更新）

完整接线、单独夹爪测试和 SO101 遥操命令见
[SO101 航凯夹爪遥操](SO101_航凯夹爪遥操.md)。

协议实现已经接到 VEL 的 `teleop_joint`、`teleop` 和 `collect`：启动时加
`--end-effector hkvr`（**口不用给**，`HKVRConfig.port` 里那条 by-id 路径就是默认值）。
不加这个参数仍然会去连因时手。
低层实现在 `算法/VEL/vel_ar5/openvla-energy/experiments/robot/ar5/drivers/hkvr_protocol.py`，
本目录的 `hkvr_gripper.py` 保留为兼容入口和离线自检。串口 I/O 由独立线程处理，
不会因为夹爪等回包而拖住机械臂循环；异常回复、CRC 错误和断线不会当成控制成功。

**2026-09-23：夹爪通了，四样硬件同时活着。** 这次实测：

| 设备 | 结果 |
|---|---|
| 臂 `192.168.2.160` | ping 通，往返 0.2 ms；本机 `192.168.2.222` 在同网段 |
| 主臂 `/dev/ttyACM0` | 6 个关节全读到 |
| **夹爪 `/dev/ttyUSB0`** | **连读 5 次全有回包**，`position=1`（全开），目标力读回 50 |
| 顶部相机 | 29.3 Hz |
| 腕部相机 | 30.3 Hz（同日稍后打通，见第 3 节） |

夹爪走 **RS485**，口用 by-id 路径（`Prolific ... ATCNl2AC568`），1 Mbps、Modbus ID 1。
**别写 `/dev/ttyUSB0`** —— 本机同时插着 CH340 和 Prolific，编号按插入顺序给，
重插一次就互换，接错的表现是完全没有回包。`HKVRConfig.port` 里那条 by-id 路径
是默认值，不用在命令行给。

早前 CAN 那条路（`--gripper-transport can`）始终没有回包，现在不用管了 ——
RS485 直连是通的。

厂家手册 `TG-9801三维触觉夹爪用户手册ver1.0.0.2.pdf` 第 4.2 节写明
RS485 / CAN（通过适配盒）。直连使用 USB-RS485：黄 A、绿 B、黑 GND、红独立 24 V。
不能把原来因时手的 USB-CAN 当 USB-RS485 使用。串口默认 1000000 baud、8N1；
如夹爪处于 RS485 自定义协议模式，先用厂家工具配置为 Modbus RTU。

力位模式的速度和目标位置必须通过功能码 0x10 一次写两个寄存器。
位置 0~1000（0 闭合，1000 全开），速度 200~1500，目标力寄存器 1~100（非牛顿）。
上电指尖初始化会走全行程，使用独立命令 `jog_hkvr --init` 显式执行；遥操不自动初始化。
驱动不写 EEPROM，也不自动修改设备 ID 或通信协议。

### ⚠ 一启动夹爪就跟着扳机走，不等你按空格

**离合只管臂，不管夹爪。** `mapper.compute()` 在没接合时返回保持姿态，但
`mapper.gripper_command(joints)` 是每帧无条件算、无条件下发的，而且**不走那 2.5 秒
接合过渡** —— 过渡只加在臂的关节上。

所以 `collect` 一连上，夹爪就立刻跑到主臂扳机当前对应的位置。2026-09-23 实测
当时的状态：

| | |
|---|---|
| 夹爪硬件 | `position=1`，全开 |
| 主臂扳机 | 45.45° → opening 0.091 → raw **780**，接近闭合 |

也就是**一启动就会合到 780/858**。指间有东西就会夹住。

**开跑之前先把主臂扳机推到张开那一端，或者确认夹爪指间是空的。**

映射实测（标定 `closed=+55.5°`、`open=−55.5°`，驱动 `POS_OPEN=0`、`POS_CLOSED=858`）：

| 扳机角 | opening | 夹爪 raw | |
|---|---|---|---|
| +55.5° | 0.000 | 858 | 闭 |
| 0° | 0.500 | 429 | 中间 |
| −55.5° | 1.000 | 0 | 开 |

**方向对不对不用猜，也不用另外写工具**：起来之后先别按空格，来回扳主臂扳机，
看终端状态行的 `手 X.XX`（预览窗右下角也有）。松开扳机数字应该往 1 走、
捏紧往 0 走。反了就把 `joint_calibration.json` 里 `gripper_closed_deg` 和
`gripper_open_deg` 对调。这一项**之前反过两次**，所以每次换主臂或重标定都要重看。

### 接通之后要注意：夹爪比回路慢得多

**闭合要 1.6 秒，张开 0.5 秒**，而采集回路是 30 Hz（33 ms 一帧）。也就是说
夹爪指令写进数据的那一刻，实际夹爪还要再走 **48 帧**才到位。这不是缺陷，
是这只夹爪的机械速度，但有两个后果要知道：

* 数据里 `action` 的夹爪维**领先**实际开合最多 1.6 秒。学出来的策略也会有这个
  相位差，评测时别当成模型抖。
* 采数据时**合拢之后要停一下再抬臂**，不然抓取还没完成臂就走了。

### 接通之前采的数据

夹爪那一维记的是**操作员扳机的位置**，不是夹爪的实际开合 —— 因为夹爪根本没动。
这批数据臂那一侧是完整的，夹爪那一维只是意图。**和接通之后采的不要混成一个
数据集。**

### 负载

夹爪自重 **400 g**，推荐负载 1500 g。`config.py` 的 `payload_mass` 还是 0，
控制器会把这部分自重当成外力。要改先把夹爪加转接板整个称一遍，别照搬 400。

## 3. 查相机

```bash
python -m experiments.robot.ar5.view_camera --list     # 扫设备，给出 by-path 写法
python -m experiments.robot.ar5.view_camera --all      # 两路并排实时看
```

没有显示器时用这个独立脚本，它抓 90 帧出一份体检（帧率、黑帧、冻帧）。
在 `dexgraspvla` 里直接跑，不用切环境：

```bash
python ~/yuhang_workspace/数据_硬件/灵巧手遥操/VR设备/view_cameras.py --check
```

**要确认三件事**：两路画面都出得来；桌面和物体都在画面里；两路各是什么视角。

### 现在装的是什么（2026-09-22 换过）

| 位置 | 相机 | USB 口 | 型号 |
|---|---|---|---|
| 顶部 | **绿联 1080P** | `10.4` | Sonix `0c45:636b`，纯 UVC 彩色，没变 |
| **腕部** | **Orbbec Gemini 305** | `10.3` | `2bc5:0840`，**RGBD**，序列号 `CV27864000V2` |

腕部这台是新接的，**换掉了原来插在 10.3 上那台绿联侧视相机**。所以现在不再是
「两路都固定在台架上」—— 顶部固定、腕部跟着臂走。

两台型号不一样了，`by-id` 能分得开。但**设备路径还是一律用 `/dev/v4l/by-path/...`**：
`videoN` 会随枚举顺序变，Orbbec 一个设备就占掉六个号，插拔一次全盘挪位。

### 腕部这台不是普通 USB 摄像头

Orbbec 一个设备占 **八个 USB 接口**，其中三个带 video 节点（2026-09-23 实测）：

| 接口 | 节点 | 报的格式 | 是什么 |
|---|---|---|---|
| `10.3:1.0` | **六个** | `Z16` / `GREY` / `BA81` / 无 | 深度和元数据。**打开会卡死** |
| `10.3:1.4` | 两个 | YUYV + MJPG | **彩色流，要的就是这个** |
| `10.3:1.6` | 两个 | YUYV | 深度。**能打开、也报 YUYV，但一帧都不给** |

**深度节点是最坑的那个。** 它的格式列表和彩色节点看起来一样，光看 `--list-formats`
区分不出来；打开也成功；然后每次 `read()` 卡满 10 秒（`select() timeout`），
默认重试 25 次就是四分多钟一动不动，而且看不出是卡在哪。

`view_cameras.py` 已经加了两道防护：先用 `v4l2-ctl` 问格式、把没有彩色格式的节点
直接跳掉；开流之后只试 4 帧就放弃，不再一路重试。但**格式相同的深度节点它挡不住**，
唯一可靠的判据是「给不给帧」，所以第一次配的时候要看着图确认哪个是彩色。

### 腕部相机通了（2026-09-23），走 UVC 不走 SDK

**两路现在都是 640x480 @ 30 Hz。** 走的是 Orbbec 的 **UVC 彩色节点**，
`config.py` 里 `cam_front` 已经改成：

```
/dev/v4l/by-path/pci-0000:0d:00.0-usb-0:10.3:1.4-video-index0
```

**接口号是 `:1.4` 不是 `:1.0`。** 原来配的 `:1.0` 是深度/元数据（`Z16`），
填错的表现不是报错，是 `read()` 每次卡满 10 秒。

**不要改用 `pyorbbecsdk`**，实测下来它反而更差：

| | UVC（现在用的） | pyorbbecsdk |
|---|---|---|
| 分辨率 / 帧率 | **640x480 @ 30.3 Hz** | 848x530 @10fps，实测 8.2 Hz |
| 装在哪 | 不用装 | **只在 `lerobot`，采集跑的 `dexgraspvla` 里没有** |
| 副作用 | 无 | **跑完把 v4l2 节点弄没** |

最后那条要特别小心：SDK 走 libuvc，会把内核 uvcvideo 从彩色接口上摘掉，
于是 `/dev/videoN` 和对应的 by-path 链接一起消失，SDK 退出也不还回来。
今天就是这么让 `--cameras cam_high cam_front` 报「路径不存在」的。

### 相机卡死了怎么救

腕部这台今天卡死过两次。症状有两种：

* **打开之后 `read()` 一直卡住**，裸 `v4l2-ctl --stream-mmap` 也卡。
  用 SDK 跑会看到一串 `setXu failed` 和 `Device response size(0)` ——
  枚举正常、控制端点不回包。
* **by-path 路径整个消失**（跑过 pyorbbecsdk 之后）。

两种都是同一个救法，软件拔插：

```bash
python -m experiments.robot.ar5.reset_camera_usb --list   # 先看现状
python -m experiments.robot.ar5.reset_camera_usb          # 复位腕部
```

**不用 sudo**（本机 `/dev/bus/usb/*` 是 `crw-rw-rw-`），复位只碰指定那一个设备 ——
主臂在 `1-10.1`、顶部相机在 `1-10.4`、腕部在 `1-10.3`，夹爪在另一条总线上，
都不受影响。复位后等 5 秒重新枚举，工具会自己把前后对比打出来。

**设备号每次都变**（今天从 63 涨到 64），所以工具是现查 sysfs 的。
自己写脚本时别把 `/dev/bus/usb/001/063` 写死 —— 上一条命令读到的号，
下一条就可能已经是 ENODEV 了。

### ⚠ 键名 `cam_front` 在新旧数据里不是同一个视角

这个键原来是**台架侧视**的绿联相机，2026-09-22 换成腕部 Orbbec 之后
**还叫这个名字**。没改名的原因：`run_ar5_eval.py` 里它已经是
`wrist_image = images["cam_front"]`，另外 5 个文件和 893 个已有文件也都用这个名字。

代价是 `~/vel_episodes` 里老的 `episode_XXXX_cam_front.mp4` 是侧视、
新采的是腕视，**光看文件名分不出来**。所以：

**新数据采到一个新目录去**，用 `--out`，别往 `~/vel_episodes` 里续。

相机跑不到 30 Hz 的两个原因（都已经在驱动里处理了，写在这里是为了将来查）：

* `exposure_dynamic_framerate` 开着，相机会拿帧率换曝光，室内光照下只给 19 Hz，
  改曝光时间、换像素格式都救不回来。连接时会自动关掉它。
* OpenCV 的 `CAP_PROP_BUFFERSIZE` 设成 1 会**正好减半**，实测 15.5 对 29.3 Hz。
  取图和还缓冲之间驱动没地方放下一帧，于是每隔一帧丢一帧。现在设的是 2。

两项都改好之后实测两路各 29.6 Hz。

## 4. 采集

**现在这套硬件（AR5 + HKVR 夹爪 + 顶部相机）的完整命令：**

```bash
conda activate dexgraspvla
cd ~/yuhang_workspace/算法/VEL/vel_ar5/openvla-energy

python -m experiments.robot.ar5.collect \
    --end-effector hkvr \
    --preview \
    --out ~/vel_episodes_wrist \
    --task "pick up the bolt and put it in the blue sleeve" \
    -n 20
```

* `--end-effector hkvr` —— **必须给**。`config.py` 里 `end_effector` 的默认值
  还是 `inspire`（因时手），不给这个参数会去连已经拆下来的手。
* `--out ~/vel_episodes_wrist` —— **换个新目录**。`~/vel_episodes` 里 893 个老文件
  的 `cam_front` 是台架侧视，新的是腕视，同名不同视角，混在一起分不出来。
* `--preview` —— 想边采边看才要，见下。
* 相机**不用点名了**，两路都通（2026-09-23），`config.py` 里配好了。
  只想采一路时才加 `--cameras cam_high`。

先只看参数、不碰硬件：把上面的命令加 `--show-config`。

### 边采边看画面（`--preview`，2026-09-23 加）

开一个本地窗口，几路相机横着拼在一起，底下一条状态：在录还是待机、第几条、
多少帧、夹爪开合、采了几条 / 目标几条。刷新 15 Hz（`CollectConfig.preview_hz`）。

**别去点那个窗口。** 按键是从终端的文件描述符读的，焦点一跑到预览窗上，
空格 / s / r / ← 全都不响应 —— 而且终端那边看着一切正常，只是你按什么都没反应。
点回终端就好了。

三件事是刻意这么做的：

* **独立线程，主回路一行都不碰。** 臂的 sender 0.25 秒收不到目标就刹车并 latch，
  而 `cv2.waitKey` 在 X 卡一下就可能超过那个数。拿一个纯展示功能去赌整条 episode
  不划算，所以 GUI 调用全在预览线程里，主回路只往一个字典写状态。
* **取图走 `cameras.peek()`，不走 `read()`。** `read()` 会推进序号并累加
  `stale_reads`（回路拿到重复帧的次数，是数据质量指标）。预览按自己的节奏取图，
  用 `read()` 会把这个数污染掉。实测 6 秒 180 次回路读 + 90 次预览取图，
  `stale_reads` = 8，跟没开预览时一样。
* **预览挂了不影响采集。** 线程里任何异常都只记在 `previewer.error` 里、退出时打一行。
  没有 `DISPLAY`（ssh 进来的）会在启动时就说，不会让你等到退出才发现。

窗口上的字是英文的：`cv2.putText` 只有 Hershey 矢量字体，没有中文字形，
写中文会一个字一个 `?` 画出来。要中文得叠 PIL 位图，为一行状态不值当。

远程那条路（`--remote`）是另一套，画面写 `live.jpg` 由代理转给网页，两者互不干扰。

### 键盘

| 键 | 做什么 |
|---|---|
| **空格** | 开始录这一条。**同时接合**，从臂开始跟主臂 |
| **P** | **保持 / 重新锚定**（**只在录制中有效**）。臂原地不动，主臂随便摆；再按一下从主臂新位置接着跟 |
| **s** | **这段做完了**：存盘 + 松开 + 臂回 0 位 |
| **r** | 丢掉正在录的这条，重来。编号不变。**臂也回 0 位** |
| **←** | **删掉刚存的那条**。只删最近一条，连按不会往回删 |
| **q** | 退出。正在录的那条不保存，要留就先按 s。**臂先回 0 位再退** |

### 0 位是哪个姿势

**s / r / q 三个出口臂都回 0 位**，这样每条的起点都一样。`←` 不回 ——
它只删磁盘上的文件，臂在哪儿不该受影响。

回的是 `joint_calibration.json` 里的 **`centre_joints`**，也就是
**主臂六个关节全零时从臂该在的姿势**。2026-09-23 验过：把主臂全零喂进映射，
算出来和 `centre_joints` 七个关节差 **0.0°**。

```
centre_joints  [-30.2, 3.2, 7.0, 90.0, -93.2, 6.2, 0.7] 度
```

**不是 `config.arm.home_joints`**（`[0.4, 18.9, -1.0, 110.4, -47.7, 3.8, -8.2]`）——
那个是笛卡尔工作空间盒的中心，两者差到 45.6°（j4）。回错的后果是每条都从偏
30~45° 的地方起步，主臂行程被不对称地吃掉一半。

要重标这个 0 位：把主臂摆到零位，`teleop_joint.py --save`。

**录着就是接合、不录就是松开。** 这两件事同进同出：不录的时候从臂跟着主臂动，
只会让你摆现场时臂在旁边乱晃，以及下一条开录时臂不在起点。

### P：主臂行程不够时用（2026-09-23 加）

臂要往一个方向走很远时，**主臂先到头了**。按 P 把臂停住、把主臂收回来、再按 P，
臂就从主臂的新位置接着往前 —— 跟抬鼠标一个道理。

```
空格 开录 → 往前推到主臂到头 → P（臂停住）→ 主臂收回来 → P（接着跟）→ … → s
```

保持期间：

* **臂原地不动。** `compute()` 不接合时返回臂自己的设定点，不是回中心位。
* **夹爪也冻住**在按 P 那一刻的开合。摆主臂时扳机难免蹭到，不冻就会把一次莫名
  其妙的开合录进数据，而画面上什么都没发生。
* **这几帧照常录，并在 npz 里逐帧标进 `held`**（bool 数组）。它们 action 接近 0、
  画面静止，两边一致 —— **不是坏数据**，只是演示里的一段停顿。训练时想丢就按
  `held` 筛。占比超过一半才会在存盘时提醒一句。
* 再按 P 之后有 **2.5 秒渐入**（`ramp_seconds`），这段臂跟得比主臂慢。

**不在录制中按 P 不起作用**，会提示你先按空格 —— 不录的时候臂本来就不跟主臂，
再给个「保持」只会让人以为按错了。

`s` / `r` / `q` 都会清掉保持状态，不会串到下一条。

**`s` 回的是映射中心，不是工作空间盒中心。** 这两个是不同的位姿，实测差到 45.6°（j4）。
映射中心才是「主臂在中位时从臂该在的姿势」；回错了每条都会从偏 30~45° 的地方起步，
主臂行程被不对称地吃掉一半。

**`r` 和 `←` 的区别**：`r` 丢的是还没存的、正在录的那条；`←` 删的是已经存到磁盘上的
上一条。正在录的时候按 `←` 不会动已存的数据，会提示你用 `r`。

**存完不会自动开下一条。** 臂自己回初始位置，你摆好现场再按空格，复位时间想用多久
用多久，没有倒计时。自动推进试过一版，问题是「下一条已经开录了但人还没摆好现场」，
数据看着正常、只是前几秒是空的。

### 采的时候注意

* **每条都要换位置。** 物体摆在同一个点采 100 条，训出来的策略只会走那一条轨迹。
* **夹爪要真的开合。** 全程不动的话 action 第 7 维是常数，那一维学不到东西。
  这是最常见的废数据，存盘时会当场提醒。
* **一条别太长。** 30 秒够做一次抓放，太长的条目里大半是空转。
* **一批之内相机路数不能变。** 一路图像的数据和两路的混不成一个数据集。
  两路现在都通了，正常就是两路一起采。中途有一路掉了就停下来救（见第 3 节的
  `reset_camera_usb`），别用一路接着采同一批。
### 臂动着动着就不跟主臂了，停在那儿

臂停下来一共**四种**原因，`collect` 原来只报第一种，另外三种默默发生 ——
「动着动着就不跟了」查不出来就是因为这个。2026-09-23 加了诊断，每秒查一次，
涨了就当场打一行并说出是哪个轴：

| 原因 | 现象 | 怎么救 |
|---|---|---|
| **latch** | 全停，程序退出并报错 | 回路堵了 >0.25s。退出重开会自动清 |
| **撞软限位** | **顶住的那个轴不动，别的还跟** —— 看着像"歪着不动" | 把主臂往回搬 |
| **跳变被拒** | **全停**，程序不报错 | **会雪崩**，见下 |
| **主臂丢包** | 对应关节这几帧不动 | 零星几帧无所谓；一直涨说明串口丢包 |

**跳变被拒为什么会雪崩**：一帧跳变超过 `joint_jump_max`（8.6°/帧，折合 258°/s）
就被驱动拒掉，而**被拒之后参考点 `_q_cmd` 不前进** —— 于是下一帧算出来还是同样大的
跳变，一路拒到底。臂就一直停在那儿，直到你**把主臂慢慢搬回拒绝发生的位置**。

所以现在屏幕上会看到这样的行：

```
  ⚠ 臂没完全跟上：目标撞软限位 30 帧（轴1 顶住了）
  ⚠ 臂没完全跟上：跳变被拒 7 次 —— **这个会雪崩**，把主臂慢慢搬回刚才的位置就能恢复
```

收工时还会汇总本次一共报了几次。**这几行不影响采集**，只是告诉你臂为什么不动。

* **臂 latch 了就停。** 程序每帧查一次，33 ms 内就会发现并退出。2026-09-03 就是
  没查这个，录出两条 600 帧一动不动的死数据。退出重开会自动清 latch。

## 5. 回放和自动检查

### 自动检查

```bash
python -m experiments.robot.ar5.qc_dataset --src ~/vel_episodes --verbose
```

查九项：丢帧 / 重复帧 / 画面丢失 / 帧率 / 卡顿 / 相机漂移 / 人手误入 / 有效动作 /
场景多样性，外加夹爪行程。

相机漂移那项只在**跨 episode 不变的像素**上量。整帧比对会被臂的起始位置和物体的
摆位带偏 —— 实测过一条整帧报 73 px、其实相机根本没动。静态区不写死坐标，
从所有首帧的逐像素标准差里自己算，换机位也不用改代码。

夹爪那项**不要拿「有没有用满 0~1」当判据**。任务用不到量程顶部不是缺陷，归一化会
自己适配。要查的是每条内部的行程、有没有合拢到底、有没有哪条全程没动。

**有两件它查不出来，只能用眼睛看**：人手有没有入镜（肤色阈值和黄胶带撞色，报出来的
基本都是误报），以及操作对不对（抓稳没有、放进去没有）。后者没有自动判据。

### 回放

```bash
python -m experiments.robot.ar5.replay                     # 列出全部，一行一条
python -m experiments.robot.ar5.replay --episode 7         # 看第 7 条
python -m experiments.robot.ar5.replay --all               # 从头一条条看
python -m experiments.robot.ar5.replay --episode 7 --cam cam_front
```

窗口里：空格暂停、`←` `→` 单帧步进、`a` `d` 上一条下一条、`q` 退出。
底部绿色条是夹爪开合，左上角是这一帧的位移量。

## 6. 删数据和编号

采集时按 `←` 就能删掉刚存的那条，npz 和两个 mp4 一起删，编号退回去让下一条重新占。

事后要删，**不要手动 `rm`**：一条是一个 npz 加两个 mp4，只删 npz 会留下孤儿 mp4，
后面的检查和转换就对不上。

### 编号有空洞不用管

续采时下一条的编号是**已有最大编号 + 1**，不是文件数。所以中间删掉一条留下空洞，
不会撞车。（原来用文件数，删掉 `episode_0150` 之后还剩 199 个文件，下一条就编
`0199` —— 而 `0199` 已经存在，**直接覆盖而且不报错**。）

空洞也不影响下游：`to_lerobot.py` 按文件名排序读，lerobot 自己重编 `episode_index`。
**要重排就等整批采完、检查完、转完之后再排一次**，中途重排会让你的回放笔记全部失效。

### 文件名不用改

`episode_%04d.npz` + `episode_%04d_<相机名>.mp4` 已经够用。任务描述、时间戳、实测
帧率都在 npz 里。把任务名或日期塞进文件名，删改和重排都会变麻烦。
**一个任务一个 `--out`**，比在文件名里区分任务干净得多。

## 7. 转成数据集

两个去向，格式要求不一样。

### 7.1 lerobot

```bash
conda activate lerobot
python -m experiments.robot.ar5.to_lerobot --src ~/vel_episodes --repo-id ar5_bolt
```

时间戳用 npz 里的 `fps_measured`，不是标称的 30 —— 回路实际跑多快事后只能靠它。

### 7.2 DexGraspVLA

格式是从 `算法/DexGraspVLA/DexGraspVLA` 的代码里读出来的，不是照论文猜的：
`controller/dataset/mask_image_dataset.py` 只读四个 key，
`controller/config/task/*.yaml` 给形状，`inference.py` 给数值约定。

```
xxx.zarr/
├── data/
│   ├── right_cam_img  (N, H, W, 3) uint8    腕部相机 RGB
│   ├── rgbm           (N, H, W, 4) uint8    头部相机 RGB + 第 4 通道二值掩码
│   ├── right_state    (N, 13) float32       实测
│   └── action         (N, 13) float32       指令
└── meta/
    └── episode_ends   (E,) int64            每条的**累计**结束下标
```

所有 episode 沿 0 轴首尾相接，`episode_ends` 是切点。它自己会断言
`data[key].shape[0] == episode_ends[-1]`。

**数值约定，三条都容易搞错：**

| 维 | 内容 | 范围 |
|---|---|---|
| 0~6 | 臂关节，**归一化**，不是弧度 | −1 ~ +1 |
| 7~12 | 手指 | 0 ~ 1，**1 是全开** |

第三条最要命：**动作是绝对值，不是增量。** `inference.py:760` 把 `action[0:7]`
直接 `scale()` 回关节限位当目标角。

**两条路都能转，但主从臂这条要多给一个参数。**

| 采集方式 | 命令 | 为什么 |
|---|---|---|
| servoJ | 默认 | 下发的本来就是绝对关节角 |
| **主从臂（本文档）** | `--action next-state` | `action` 栏是位姿增量用不了，但**七个关节角本来就在 `state` 里** |

主从臂这条的做法是：**拿下一帧的实测关节角当这一帧的动作**，最后一帧原地重复。
这是绝对位置动作空间的标准重建法，策略学的是「下一步该到哪」。
不给这个参数脚本会拒绝并说明原因，不会悄悄转出一份错的。

**这个做法有一处代价**：下一帧的状态是**实测值不是指令值**，中间隔着一层跟踪误差。
真正下发的关节角我们没存。影响是学到的动作比真实指令钝一点、幅度略小。
要更准就得在 `collect.py` 里把下发值也存一份 —— 那是改采集，不是改转换。

```bash
conda activate dexgraspvla
cd ~/yuhang_workspace/数据_硬件/灵巧手遥操/VR设备

# 主从臂采的（本文档这条路）
python to_dexgraspvla.py --src ~/vel_episodes/11 --dst ~/atom_grasp.zarr \
    --action next-state --wrist-cam cam_front --head-cam cam_high

# servoJ 采的
python to_dexgraspvla.py --src ~/atom_episodes --dst ~/atom_grasp.zarr \
    --wrist-cam cam_front --head-cam cam_high
```

转完可以直接用它自己的 dataset 类验（实测过）：形状 `rgbm (1,4,518,518)`、
`right_cam_img (1,3,518,518)`、`right_state (1,13)`、`action (horizon,13)`，
normalizer 也能拟合。

**13 维 = 7 臂 + 6 手，和 AR5 加因时手严丝合缝。** 换成一维夹爪就是 8 维，
要同步改它 `controller/config/task/` 那个 yaml 里的 `right_state.shape` 和
`action.shape`，而且**预训练 checkpoint 的维度对不上，不能微调，只能从头训**。
脚本跑完会把该改的值打出来。

**掩码那一路是真障碍。** `rgbm` 第 4 通道是目标物体的二值掩码，官方用 SAM 生成、
Cutie 逐帧跟踪 —— 那是它判断「抓哪个」的唯一输入。脚本的 `--mask none`
先全填 255 把链路跑通，但**这样训不出对的东西**，跑完会警告。

## 附：写盘为什么在后台线程

实测 600 帧 + 2 路相机同步存盘要 **2.21 秒**，而臂的 sender **0.25 秒**收不到目标就
刹车并 latch。在回路里同步存盘等于每存一条就有一次锁死机会。2026-09-03 就是这么
废掉三条数据的：第一条存的时候臂正好停着，侥幸活了；第二条存的时候臂还在动，
锁死，之后 600 帧 × 2 条全是一动不动的死数据。
