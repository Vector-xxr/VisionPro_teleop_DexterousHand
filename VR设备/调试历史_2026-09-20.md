# Vision Pro → AR5 + 因时 RH56 遥操

左手驱动机械臂末端位姿 + 灵巧手五指，右手捏合当离合（dead-man）。

| 文件 | 作用 |
|---|---|

| `movel_stream.py` | MoveL 路点流式下发（`--arm-backend movel` 走这条）。本地缓存 + 分频批量下发也在这 |
| `mock_movel.py` | 内存假 MoveL 控制器，让 movel 后端能在 `--mock` 下跑完整条链路 |
| `home_arm.py` | **把臂送回起始姿态**（关节空间 MoveAbsJ，不开 RT）。遥操没跑时用；跑着按 `h` |
| `ar5_ik.py` | 逆解。`AR5OptIK`（优化式，默认）/ `AR5IK`（雅可比迭代） |
| `ar5_poe_ik.py` + `paden_kahan.py` | 旋量法解析解（1.93ms / 残差 0.0000mm） |
| `hand_retarget.py` | 25 关节手骨架 → 手的 6 维；判手心手背 |
| `inspire_hand6.py` | 灵巧手驱动（CAN over USB 透传） |
| `vel_kin.py` | 按文件路径加载外部运动学模块（绕开同名包遮蔽） |

## 执行命令

```bash

python avp_arm_teleop.py 192.168.0.246 --no-cameras --arm-backend movel \
```

右手捏合接合，再捏一次松开。左手驱动臂的末端位姿和五指。

**只有三个值要自己填**，其余默认值就是实测调出来的最优：

| 参数 | 怎么来的 | 不填会怎样 |
|---|---|---|
| `<头显IP>` | Tracking Streamer 界面上读，**每次可能变** | 连不上，卡在等头显 |
| `--yaw` | 现场测一次（见下面「坐标系」一节），推导值 `-90` | 前后左右整体转 90°/180°，姿态也一起错 |
| `--payload` | 手的质量 kg | 默认 0 → 控制器把手的自重当碰撞 → **抱死掉电** |

已经调好、不用动的：`--arm-backend movel`（逆解交控制器，实测 37ms）、
`--movel-speed 250`、`--movel-deadband 3.0`、`--movel-lead-ms 50`、
`--arm-smooth 1.0 --arm-smooth-beta 3.0`。要调见「常用参数」。

> **`--hz 100 --movel-dispatch-hz 20` 是本地缓存那一版**（见「本地缓存」一节）。
> ⚠ **配 `--movel-deadband 3.0` 时每批只有 1 个点，等于缓存没起作用** ——
> 要让它真的成批，死区得降下来（1.0 → 均 2.1 点，0.5 → 3.4 点）。
> 但降死区在真机上是涨延迟的（旧架构实测 0.5mm=73ms vs 3.0mm=37ms），
> 所以这两个数得在真机上一起定。不想动就照默认 `--hz 50` 跑，行为和以前一样。

> 左右反了、翻手掌没反应 → 「坐标系」一节。
> 臂抖、延迟高、动两下不动 → 「臂怎么驱动」一节。
> 其他症状 → 文末「出问题看哪里」。

## 坐标系：`--yaw` 与 `--mirror`（左右反了 / 翻手掌没反应，都看这里）

**头显系：X = 右，Y = 前，Z = 上**，单位米，原点为应用启动时头显位置。
依据是 `avp_stream/streamer.py` 的 `YUP2ZUP = Rx(-90°)`，作用在 visionOS 的
(X右, Y上, Z朝后) 上。*（本文件早先写的「X 向前、Y 向左」是错的。）*

**臂基座系：X = 前，Y = 左，Z = 上。**

两者之间只差一个绕 Z 的旋转 `--yaw`，它**同时**决定平移和姿态：

```
p_target += R @ (手的位移)          R = yaw_matrix(--yaw)
R_rel     = R @ (Δ手的姿态) @ Rᵀ    ← 转轴会被 R 一起搬走
```

所以 yaw 错一个值，位置和姿态会**一起**错，而且表现看着像两个毛病：

| yaw | 手往右→ | 手往前→ | 翻手掌（绕前臂滚转）落到 |
|---|---|---|---|
| 0（旧默认） | 臂往**前** | 臂往**左** | 臂的左右轴 → 变成末端**俯仰**，手心手背分不出来 |
| **-90** | 臂往**右** ✓ | 臂往**前** ✓ | 臂的前后轴 → 末端**滚转** ✓ |
| 90 | 臂往**左** | 臂往后 | — |
| 180 | 臂往后 | 臂往**右** | — |

**推导值是 `-90`**，但你站的方位和臂的安装朝向决定实际值，现场用 `probe_axes.py` 测一次。

### 但如果是**镜像**，yaw 修不了

「左右反了、前后是对的」在数学上**不是旋转，是反射**：

| | 行列式 | 能否由 yaw 得到 |
|---|---|---|
| 旋转 | +1 | 能 |
| **反射** | **−1** | **不能，取任何角度都变不出来** |

yaw 转 180° 会把前后**一起**翻掉，所以只翻左右的现象，调 yaw 永远调不好。
用 `--mirror`：

```bash
python avp_arm_teleop.py <头显IP> --no-cameras --yaw -90 --mirror lr
```

| 选项 | 翻什么（头显系 X=右 Y=前） |
|---|---|
| `--mirror lr` | 只翻左右（翻 X） |
| `--mirror fb` | 只翻前后（翻 Y） |

合成后 `A = R_yaw @ M`，平移 `p → A p`，姿态 `R_rel = A ΔR Aᵀ`。
det(A) = −1，但 **det(R_rel) = +1**（实测偏差 1.6e-15）—— 共轭出来仍是正经旋转，
不会给臂送一个带反射的姿态（那是无解的）。物理含义：臂看到你动作的镜像，
手转的方向也跟着镜像。

### 手心 / 手背怎么判的

**不看手腕矩阵**，直接从骨架算（`hand_retarget.palm_frame`）：
用手腕 + 食指/中指/小指指根三个掌骨点，显式叉乘建右手正交系，
掌法向 = 第三轴。

为什么不用 `left_wrist` 的旋转矩阵：visionOS **左右手腕系的约定不一样**，
`avp_stream/utils/trn_constants.py` 里

```python
VISIONOS_RIGHT_HAND_TO_LEAP = ROTATE_90DEG_AROUND_X @ ROTATE_NEG_90DEG_AROUND_Y
VISIONOS_LEFT_HAND_TO_LEAP  = ROTATE_90DEG_AROUND_X @ ROTATE_90DEG_AROUND_Y
```

差一个 ±90° 绕 Y。骨架没这个问题——解剖学的手掌平面和厂商怎么定义手腕系无关。
而且显式叉乘保证 **det 恒为 +1**（500 个随机骨架实测偏差 6.7e-16），
左手数据绝不会退化成镜像。

⚠ **掌法向的符号没在真机上验过**：左手骨架的实际排布决定它是从手心还是手背穿出。
`probe_axes.py` 里手心朝下时如果报「手心朝上」，就是符号反了，改一行的事。

## 臂抖：输入滤波

Vision Pro 的手腕位姿本身带抖动，而臂这条路**原来一点滤波都没有**
（`--smooth` 只喂给手的重定向），噪声原样进 IK 就变成关节指令。

现在默认过一层 **One-Euro**：截止频率跟着速度走 `fc = min_cutoff + beta·|v|`，
手停住时压得死、快速挥动时几乎不引入延迟 —— 普通一阶低通做不到这一点
（压得住抖就一定发糊）。

按 3mm 噪声建模扫出来的取舍（**噪声幅度是估的，没实测过真机**）：

| `--arm-smooth` / `beta` | 静止残余抖动 | 20cm/s 滞后 | 60cm/s 滞后 |
|---|---|---|---|
| 关闭（旧行为） | 3.04 mm | 0 | 0 |
| **1.0 / 3.0（默认）** | **0.82 mm** | 10.3 mm | 17.6 mm |
| 0.8 / 2.0 | 0.85 mm | 12.7 mm | 22.7 mm |
| 2.0 / 10.0 | 1.15 mm | 5.3 mm | 8.6 mm |

还抖 → `--arm-smooth 0.6`；觉得发糊/跟不上 → 调大 `--arm-smooth-beta`。

## 臂怎么驱动：`--arm-backend`

两条路，语义完全不同：

| | `rt`（默认） | `movel` |
|---|---|---|
| 逆解在哪 | **本地**（旋量法 PoE / 优化式，1.9~2.7ms） | **控制器**（本地只算绝对位姿） |
| 下发什么 | 7 个关节角，1kHz | 笛卡尔位姿路点，~50Hz |
| 语义 | **覆盖式**：新指令盖掉旧的 | **提交任务式**：每个点都会被执行完 |
| 零空间 | 本地管（可 `--lock-j5`） | 控制器 `setDefaultConfOpt(False)` 取最近解 |
| 实测延迟 | — | **37ms 中位**（250mm/s + 3mm 死区，带 0.82mm 手抖） |

```bash
python avp_arm_teleop.py <头显IP> --no-cameras --yaw -90 \
    --arm-backend movel --payload 1.0 --payload-com-z 0.08
```

现场反馈 movel「丝滑不少」：分支选择和轨迹平滑都交给了控制器。
代价是**队列语义**，下面两条坑都是这么来的。

### 延迟有两个旋钮，**死区比速度更管用**

#### 旋钮一：前导距离（`--movel-speed` / `--movel-lead-ms`）

队列深度拿不到（`wayPointIndex` 是**批内**下标，单条 append 时恒为 0），
所以用前导距离代替：

    延迟 ≈ (最后一个已下发目标 − 当前实测位置) / 速度

超过 `--movel-lead-ms` 换算出的上限就**跳过这一帧**（目标是「最新值」，
不是必须执行的轨迹段）。**干净**输入下走走停停实测：

| `--movel-speed` | 延迟 | 跳帧率 |
|---|---|---|
| 150 | 66ms | 52% |
| **250（默认）** | 41ms | 30% |
| 400 | 41ms | 21%（但现场反馈「太快了」） |

**嫌延迟高先提 `--movel-speed`，别去降 `--movel-lead-ms`** ——
降预算只让跳帧率飙升，延迟反而降不下来。

> ⚠ 上面这张表是拿**完全干净**的目标测的，偏乐观。同样 250mm/s，
> 换成带 0.82mm 手抖的真实输入，延迟是 **73ms** 不是 41ms。原因见下。

#### 旋钮二：抖动死区（`--movel-deadband`）

**前导距离是直线距离，可队列里排的是一条折线。** 目标带抖动时折线远比
直线长，而排队式是每个点都必须走完的 —— 臂在追噪声，延迟就涨，
而且 `lead/speed` 这个估计会**低估**真实延迟。

One-Euro 之后仍有约 0.82mm 残余抖动（见上一节）。死区比它小，抖动就被原样
塞进队列。拿 0.82mm 抖动 + 0.4Hz 正弦实测：

| `--movel-deadband` | 延迟中位 | p95 | 跟踪 RMS | 位移 |
|---|---|---|---|---|
| 0.5mm | 73ms | 114ms | 19.7mm | 39.2mm |
| 1.5mm | 61ms | 133ms | 19.8mm | 39.7mm |
| **3.0mm（默认）** | **37ms** | **93ms** | **14.2mm** | 40.2mm |

延迟砍掉一半，而且跟踪精度**反而变好**。

原理不是「少发点省带宽」，而是：**短段是加速度受限的，臂根本跑不到指令速度。**
抖动路径上实测臂只有 **25~33mm/s**，而指令是 250mm/s —— 段被抖动切碎，
每段都在加速阶段就结束了。死区把段拉长，臂才提得起速。

死区对真实运动**零滞后**（过了阈值原样通过），这一点比继续加大 One-Euro 强：
加滤波是全频段都拖慢，死区只砍幅度小于阈值的。

**死区不会吃掉精细动作，反而更准。** 8 秒缓慢走 6mm（0.75mm/s，比死区本身还慢）：

| `--movel-deadband` | 实到 | 下发条数 |
|---|---|---|
| 0.5mm | 3.79mm | 214（臂在追噪声，跟不上） |
| **3.0mm** | **6.01mm** | 2（精准到位） |

因为死区是对**上一个已下发点**的增量阈值 —— 慢速运动会累积过阈，一个都不丢，
只是把位置量化到 3mm。真嫌粗就 `--movel-deadband 1.0`，延迟会涨回去。

### 本地缓存：`--hz` 与 `--movel-dispatch-hz`

原来采样和下发锁死在一起（采一帧就 append 一次）。现在拆成两级：

```
--hz 100              每帧：One-Euro → 算绝对位姿 → 死区 → **进本地缓存**（不碰 SDK）
--movel-dispatch-hz 20  每 50ms：读位姿 → 判空闲 → 前导闸门 → 抽稀 → 批量 append
```

`--movel-dispatch-hz 0` = 采样即下发（旧行为）。

**为什么这么拆**（不是为了省 `moveAppend` 的时间，单发 0.03ms，攒批每点只省
0.008ms，在帧预算里等于零）：

- **采样能独立提速**。100Hz 把量化误差从 20ms 降到 10ms，而 SDK 的接触次数
  反而从 100 次/秒降到 20 次/秒 —— 绑定不放 GIL，每次 SDK 调用都是主循环的
  独占开销，次数少是实打实的。顺带 `moveStart` 那 42.8ms 的顿挫也被限到
  最多 20 次/秒（它只在 flush 里发生）。
- **路径保真**。一次交多个点，控制器拿到折线而不是孤立终点。

**代价**：下发前多等 0~50ms（均值 25ms）。嫌大就**提** `--movel-dispatch-hz`，别降。

#### ⚠ 死区决定缓存到底有没有用

100Hz 采出来的帧大部分被死区拦掉，所以**每批几个点是死区说了算，不是采样率**。
mock 实测（12 秒，同一段运动）：

| `--movel-deadband` | 进缓存 | 每批均点数 | 最大 |
|---|---|---|---|
| **3.0mm（默认）** | 168 | **1.0** | 1 ← 缓存等于没起作用 |
| 1.0mm | 421 | 2.1 | 3 |
| 0.5mm | 690 | 3.4 | 5 |
| 0.2mm | 939 | 4.6 | 5（满批 = hz/dispatch-hz） |

所以「100Hz + 20Hz」要真有意义，死区必须一起降。而降死区在旧架构上是涨延迟的
（0.5mm=73ms vs 3.0mm=37ms）——**这两个数只能在真机上一起定**。

> 一个尚未验证的推测：新架构里抽稀是在 flush 时**带着整批一起看**前导预算做的，
> 旧架构只能逐帧决定、没有前瞻。所以低死区 + 抽稀也许能达到旧架构达不到的平衡。
> 真机上跑一次才知道。

#### 批量提交：`moveAppend(list[MoveLCommand], ...)`

SDK 的 `moveAppend` 有两组重载（实测 `R.moveAppend.__doc__`，13 个重载）：

```
#2  moveAppend(cmds: list[MoveLCommand], cmdID, ec)    ← 批量
#8  moveAppend(cmd:  MoveLCommand,       cmdID, ec)    ← 单条，原来走这个
```

现在默认走 **#2**（`--no-movel-batch-append` 退回逐条）。

**动机不是省时间** —— 单发 0.03ms、20 条批量 0.44ms，每点只省 0.008ms，在帧预算里
等于零。动机是：**一次提交一串点，控制器有机会把它们当一条连续路径来规划、段间做
转弯区混合；逐条提交则每条都是一个独立任务。** 这正对着「执行一段会钝一下」。

> ⚠ **这是假设，没在真机上验过。** 厂商没说批量和逐条的规划语义有区别。
> 真机判据：同样的批大小下，批量提交能不能让**队列跑空次数**下降。

**⚠ 批大小为 1 时两者完全等价**，所以默认 3mm 死区下这个开关**没有任何效果**。
mock 实测（10 秒同一段运动）：

| `--movel-deadband` | 批量开 | 批量关 |
|---|---|---|
| **3.0（默认）** | 133 点 / **133 次调用** | 133 点 / 133 次 ← **一模一样，批量从没触发** |
| 1.0 | 324 点 / **159 次** | 324 点 / 324 次 |
| 0.5 | 530 点 / **164 次** | 531 点 / 531 次 |

**要让批量起作用，死区必须先降到 ≤1.0mm**（或把 `--movel-dispatch-hz` 降下来），
让每批攒到 ≥2 个点。退出统计里看 `moveAppend: N 点 / M 次调用（其中批量提交 K 次）`。

失败语义也变了：批量只有**一个** `ec`，分不出是哪一条出的问题，所以按**全批失败**
处理（不推进 `_last_target`）。若 SDK 抛 `TypeError`（重载不匹配）会自动退回逐条并记账。

> 顺带：SDK 里还有 **`MoveSPCommand`**（样条）也支持批量重载。对"连续路径"这个
> 目标可能比 MoveL 更对症，**还没查**。

#### 队列语义决定了一批不能无脑全塞

进了队列的点控制器**必须挨个走完**，所以一批的代价是它们连成的**折线长度**。
flush 里按前导预算抽稀：装得下就全发；装不下按步长 2,3,4… 抽，**永远保留最新
那个点**；抽到只剩最新一点仍超预算就照发（不发会让 `_last_target` 永不前进、
前导恒 0，下一批同样局面 —— **永久卡死**）。

两条容易想错的：

- **保留最新点**不是随意选的：发的是**绝对位姿**，最新点已包含被丢弃中间值的
  全部信息。丢新留旧对遥操是反的。也正因为是绝对位姿，抽稀不会「少走一段」——
  增量语义才会。
- **直线运动上抽稀一点用都没有**。任何以最新点收尾的子集，折线长度都 ≥ 起点到
  最新点的直线距离。抽稀只在路径**带抖动**（折线远长于直线）时才回收得到预算 ——
  和死区是同一个道理的两面。

退出统计里看这几项：`每批均 N 点`（缓存有没有在用）、`抽稀丢`、`单点超预算`
（次数多 = 手速常态超过预算，提 `--movel-speed` 或 `--movel-lead-ms`）、
`缓存溢出丢`（flush 被拖住了）。

### 「执行一段动作会钝一下，再执行下一段」= 队列跑空

**机制**：MoveL 是队列语义，队列一走光 → 臂**减速到 0**（没有下一段，`--movel-zone`
的转弯区无从混合）→ 新点到了要补 `moveStart`（往返 42.8ms + **首次运动 127ms**）
→ 约 **170ms 死时间**，前后还各带一次完整加减速。

**什么时候跑空**，把两个速率一比就出来了：

```
点到达间隔  = 死区 ÷ 手速
一段执行耗时 = 死区 ÷ 臂速
```

**死区约掉了** → 跑空的条件就是 **`手速 < 臂速`**。臂在短段上加速度受限，实测
25~33mm/s。所以手速掉到约 30mm/s 以下（一段动作收尾时必然如此）队列就空。

这正是「阶段性丝滑」的来源：手快挥时点供得上，队列不空，转弯区连续混合 → 丝滑；
手一慢就跑空 → 钝一下。

> ⚠ **调死区治不了这个**，它在上面那个比值里约掉了。

**诊断**：跑起来按 `s`，或看退出统计：

```
卡顿诊断（10.4s）：**队列跑空 168 次**（16.2 次/秒）  臂空闲占比 100%[采样值]
  手速 45mm/s  vs  臂平均速度 50mm/s  → **臂比手快 → 会跑空**
```

跑空次数以 `restarts` 为准（`moveStart` 返回 ec=0 才算，控制器亲口说的）。
**不能用采样到的 idle→moving 跳变** —— 空闲是在 flush 里按下发频率采的（50ms），
段比这还短时跳变会被整个漏掉，实测出现过「空闲占比 100% 但跑空 0 次」这种
自相矛盾的读数。

**对症：让臂别比手快 → `--movel-adaptive-speed`**

`MoveLCommand.speed` 本来就是**逐段**的（原来写死 250）。开了之后：

```
段速 = clamp(手速 × --movel-speed-gain, --movel-min-speed, --movel-speed)
```

手慢 → 段也走得慢 → 执行耗时和点到达间隔匹配 → 队列不空；手快 → 顶到
`--movel-speed`，和原来一样。跑起来按 `a` 开关，`,` `.` 调 gain。

**gain 是「跑空(钝) ↔ 滞后(跟不上)」取舍线上的位置**，两头都难受（mock 12 秒）：

| gain | 队列跑空 | 进缓存→下发 | 超前导丢 |
|---|---|---|---|
| 1.0 | **1** | 206 → **25** | **181（88%）** ← 不钝了，但臂严重滞后 |
| 1.1 | 42 | — | — |
| **1.3（默认）** | 125 | 168 → 163 | 5 |
| 2.0 | 156 | — | — |

gain=1.0 之所以不跑空，是因为臂**一直欠着债**从不空闲 —— 那不是丝滑，是滞后。

> ⚠ 这张表是 mock 的，而 **mock 没有 `moveStart` 的 170ms 代价、也没有加速度限制**。
> 真机上每次跑空要真金白银付 170ms，所以真机的最优 gain 会和这张表不一样。
> 现场用 `,`/`.` 扫：**钝就调小，跟不上就调大**，盯 `跑空次数` 和 `超前导丢` 这两个数。

### 「动两下就不动了」

队列走光臂就停，得补一次 `moveStart`（42.8ms 往返）。判「停没停」
**必须问控制器 `operationState`**，不能看位置。这里踩过两个坑，症状一样：

- 用「距上次 append 多久」判 —— 臂完全能在持续 append 的情况下把队列走光，
  那时判据恒假，新点永远没人启动。
- 改看位置（连续 N 帧不动，≈60ms）仍太急 —— 臂物理上停了但控制器状态还没退，
  `moveStart` 被拒 `ec=-20`，14 秒里 14~20 次。而且 `moveStart` 失败是
  **返回错误码不抛异常**，不查 `ec` 就会当成功。

换成 `operationState != moving` 后降到 0~1 次（0.093ms/次，每帧查得起）。

### `moveStart` 的返回码：哪些是真失败

`diag_movel_state.py` 逐个问出来的（**这三条别再猜**）：

| ec | 含义 | 真失败？ |
|---|---|---|
| 0 | 成功 | — |
| **−20** | 机器人运动中 | **否**。运动中 append 的点会被控制器**自动接上执行** —— 实测指令 6mm 实到 6.0mm，不用补 start |
| **768** | 没有可执行的运动指令（队列已空） | **否**。没东西要跑 |

我一度把 −20 当成「点会搁浅」，改成保留欠账、空闲时补发 —— 结果在队列已空时
空放，14 秒报 **28 次「失败」**，吓人但无害。现在两个码都归良性，
退出摘要里分开记 `已在动` / `队列空`。

### `operationState` 靠得住吗

靠得住，而且**偏保守**。同一段 6mm 的 MoveL：

```
位置停稳       270 ms
状态退 moving  357 ms      → 状态比位置晚 87ms
状态序列       moving → idle
```

方向是对的：它绝不会在臂还在动的时候说 idle，只会晚一点说。
（反过来用位置判就会早说，那正是 `ec=-20` 刷屏的原因。）

### 重启那 42ms 的顿挫：没法用多线程绕开

`moveStart` 是**同步往返 42.8ms**，而且恰好落在运动恢复的瞬间
（`update()` 实测 p95 43ms、最大 87ms，50Hz 只有 20ms 预算）。
把它扔到工作线程上试过了，**一点用没有**：

```
             update()中位   p95      最大    延迟中位  延迟p95
同步(现状)       1.14ms  43.20ms   87ms     41ms    92ms
异步(工作线程)   1.18ms  43.81ms   87ms     42ms    90ms
```

根因是 `try_async_start.py` 的 L1 量出来的：两个线程同时查状态 5 秒，
**工作线程 26503 次、主线程 1 次** —— xCoreSDK 的 Python 绑定
**在整个 C++ 调用期间不释放 GIL**，工作线程一进 SDK 调用就把主线程饿死。
所以换线程发 moveStart 毫无意义，这条路封死。

> 反过来也要记着：**任何后台线程做 SDK 调用都会饿死遥操主循环**。
> 排帧预算时把每个调用的耗时直接加进去：`cartPosture` 0.177ms、
> `operationState` 0.093ms、`moveAppend` 0.03ms 都便宜，
> 而 `moveStart` 42.8ms、`checkPath` 42ms 是炸弹。

> RT **笛卡尔**模式是第三条路，已验死：收指令但不动（20mm 指令实到 0.4mm
> 且不随指令变）。复验脚本 `try_cartesian_rt.py` / `diag_cartesian_rt.py`。

## 锁 j5（消冗余）

```bash
python avp_arm_teleop.py <头显IP> --no-cameras --yaw -90 --lock-j5 0.0
```

j5 是 ±50° 的两个窄轴之一。锁死它 → 7 轴降 6 轴，**冗余消失、零空间没了**，
肘不会再自己换边；而且这根最容易顶限位的轴被摘出了问题。
实测：不锁时 j5 行程 16.7°，锁上之后 **0.000°**。

代价是任务空间少一个自由度，够不到的位姿变多——由 best-effort 打滑兜底。

⚠ 只对 `--arm-backend rt` 有效。`movel` 下逆解在控制器里，锁不了单轴。

## 零空间（7 轴解 6 维位姿）

位姿只定 6 维，第 7 个自由度（肘部绕「肩—腕」连线转）**位姿定不住**。
不给偏好的话肘会在零空间里随机游走：TCP 没怎么动，肘自己换边。

现在的做法是把冗余拉向 `config.arm.home_joints`（挑过的工作姿态，
没有一个轴用超过 68% 行程），肘就稳定停在一个人看得懂的位置。

⚠ **做不到「肘跟着你的肘走」**：Tracking Streamer 只给头 + 手腕 + 每只手 25 个
手指关节，**没有肘、没有肩**。要真的复制人的臂型，得另外加上肢追踪。

## 「跑到某个位姿就抱死」

抱死 = 碰撞检测触发 → 硬停 → 掉电 → 抱闸（同时 RT 会话被打断，控制器残留
`rtControlling`，之后排队式 `Move*` 全被拒报 `ec=262`。**这是一次触发的两个症状**）。

下发前有两道本地校验（都在 `AR5OptIK` 里，合计约 0.1ms）：

| 校验 | 做什么 |
|---|---|
| 关节限位 + 单帧步长 | 写成 box 硬约束，解出来天然合法 |
| **近奇异减速** | 可操作度 `w < min_manip(0.01)` 时按 `w/min_manip` 缩步长，地板 15% |

奇异减速是**减速不是拦截**：拦截会把臂锁死在奇异点上出不来（第一版就是这么写的，
自检里 40 帧全被拦、可操作度纹丝不动）。留 15% 地板保证永远走得出来。
注意它**不阻止**臂进入奇异位形，只是让它慢慢进——目的是不让伺服跟随误差变成力矩尖峰。

> 为什么不用驱动现成的 `check_reachable`：它走 `robot.checkPath`，是控制器往返，
> `ar5_env.py` 里量过 **42ms 且持 GIL**。50Hz 只有 20ms 预算，而且会饿死 1kHz 的
> RT 发送线程。那个函数本来就注明「绝不用在 RT 路径上」。只能在接合前偶尔调。

**但最大嫌疑是负载没设。** `--payload` 默认 0，而手有 0.8~1.4kg。未建模的重力矩
**随位姿变**（臂伸得越远、越水平，力矩越大），控制器把它当成外力 → 判成碰撞。
这正好解释「到某个位姿才抱死」。先试：

```bash
python avp_arm_teleop.py <头显IP> --no-cameras --payload 1.0 --payload-com-z 0.08
```

填个近似值也远好过 0。测准的办法：臂静止水平伸出，读 `get_external_force()`。

碰撞灵敏度已经在 `ArmConfig` 里放宽过了（`collision_sensitivity=0.3×7`，
`suppleStop`），**数值越小越不灵敏**，而且这个设置活不过控制器重启。

## 常用参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `--arm-backend {rt,movel}` | `rt` | 臂怎么驱动。`movel`=逆解交控制器，现场反馈更丝滑 |
| `--movel-speed` | 250 | movel 的末端线速度 mm/s。嫌延迟高先提这个，别降 lead-ms |
| `--movel-deadband` | 3.0 | movel 的抖动死区 mm。**延迟最有效的旋钮**（0.5→3.0mm 砍掉一半延迟）。精细抓取嫌粗就降到 1.0 |
| `--movel-lead-ms` | 50 | movel 的延迟预算。换算成前导距离上限，超了就跳帧 |
| `--hz` | 50 | 采样频率。提到 100 可以把量化误差减半；`--slip-after`/`--relimit-after` 是**帧数**，没显式给时会按 hz 等比缩放保持时长不变 |
| `--movel-dispatch-hz` | 20 | 本地缓存交给控制器的频率。`0`=采样即下发（旧行为）。⚠ 每批几个点由**死区**决定，不是采样率 |
| `--movel-batch-append` / `--no-...` | **开** | 走 SDK 的批量重载一次提交整批。⚠ 每批 1 点时无效果，要先把死区降到 ≤1.0 |
| `--movel-adaptive-speed` | 关 | 逐段速度跟着手速走。**对症「执行一段会钝一下」**（队列跑空）。跑起来按 `a` 开关 |
| `--movel-speed-gain` | 1.3 | 自适应段速里臂比手快多少倍。**跑空(钝) ↔ 滞后(跟不上)** 的旋钮，`,`/`.` 现场调 |
| `--movel-min-speed` | 20 | 自适应段速的下限 mm/s |
| `--movel-buffer` | 64 | 本地缓存上限，满了丢最老的。只有 flush 被拖住才会满 |
| `--arm-smooth` | 1.0 | 臂输入去抖(One-Euro 最小截止频率 Hz)。**臂抖就往小调**，如 0.6；0=关掉 |
| `--arm-smooth-beta` | 3.0 | 越大=快速运动越跟手，但抖动放得越开 |
| `--lock-j5` | 不锁 | 把 j5 锁死在给定弧度，只用其余 6 轴解。消冗余，肘不再换边（只对 `rt` 有效） |
| `--yaw` | 0 | 头显系绕 Z 转多少度喂给臂。**必须用 `probe_axes.py` 测**，错了位置和姿态一起错 |
| `--mirror {none,lr,fb}` | `none` | 反射。「左右反了但前后对」只能靠它，yaw 修不了 |
| `--payload` / `--payload-com-z` | 0 / 0 | 手的质量(kg)和质心。**默认 0 会让控制器把手的自重当碰撞** |
| `--ik {opt,dls,stock}` | `opt` | 逆解路线。出问题先退 `dls` |
| `--gain` | 0.5 | 绝对伺服增益。大=跟得紧但顿挫，小=丝滑略滞 |
| `--scale` | 1.0 | 手动 1m，末端动多少 m |
| `--no-rotation` | 关 | 只跟位置不跟姿态 |
| `--rot-mode roll` | `full` | 只跟手掌「拧」，不跟上下挥 |
| `--max-lead` / `--max-rot-lead` | 0.04m / 0.35rad | 两条缰绳，指令能领先实测多少 |
| `--freeze-thumb-rot` | 关 | 拇指旋转不跟踪，做精细捏取时建议开 |
| `--hand-debug` | 关 | 查「单独弯某根手指没反应」 |
| `--no-home` | 关 | 不回起始姿态。**一般别关**，j5/j6 只有 ±50° |

## 出问题看哪里

| 症状 | 看这里 |
|---|---|
| **前后左右整体转了 90°/180°** | `--yaw` 不对。跑 `probe_axes.py` 定值 |
| **左右反了、但前后是对的** | 这是**反射不是旋转**，yaw 修不了。加 `--mirror lr` |
| **翻手掌（手心↔手背）没反应，变成上下挥** | yaw 错时滚转被搬到俯仰轴上。先修 yaw/mirror |
| 掌向报反了（手心朝下却说朝上） | `palm_frame` 的掌法向符号反了，告诉我改一行 |
| 肘部自己换边、臂型不可预期 | 零空间没约束。见上面「零空间」一节 |
| 手还没伸多远臂就到头了 | `--scale` 太大。竖直方向只有 ±170mm，见「空间范围对齐」 |
| **臂很抖** | 臂这条路以前**没有任何滤波**（`--smooth` 只喂手）。现在默认开了 One-Euro；还抖就 `--arm-smooth 0.6`，发糊就调回 1.5 |
| 臂一动不动、日志刷 `goal jumps ... refusing` | 逆解解支跳变。确认在用 `--ik opt` |
| 臂快速走到限位卡住 | 见 `ar5_ik.py` 里 `AR5OptIK` 的文档；跑 `test_changes.py` 的【回归】段 |
| **`movel` 下臂动两下就不动了** | 队列走光没人重启。退出摘要看 `moveStart 失败 N 次`（`已在动`/`队列空` 都是良性的，不算）。见「臂怎么驱动」一节 |
| **`movel` 下延迟高** | 先提 `--movel-deadband`（最有效，臂在追手抖）；再提 `--movel-speed`。**不要**降 `--movel-lead-ms` |
| **`movel` 下小幅动作跟不动 / 一顿一顿** | `--movel-deadband` 太大，位置被量化了。降到 1.0 |
| **整只手都不动** | 先看开机横幅那行 `手 :`。写着【无】就是命令里带了 `--no-hand`，去掉即可。写着真手/假手再往下查 |
| 手接上了但还是不动 | 退出摘要看 `手: 写 N 次`。N=0 = 上游没给指令，再看有没有 `重定向出错`；N>0 却不动 = 手/机械的事 |
| 某根手指不动 | 先 `test_fingers.py`：那里能动=头显没跟踪到；不能动=手/驱动的事 |
| 六维全不动、I/O 错误却是 0 | 手处在「通信活着、控制循环死了」的半死状态。**拔手自己的 24V**（不是 USB），等 5 秒再上。判据：温度读数会变 |
| 急停 | 默认自动清（`recoverState(1)`）。这台臂没有物理急停按钮 |
| **跑到某些位姿就抱死** | 先怀疑 `--payload`（默认 0，而手有 0.8~1.4kg）。未建模的重力矩是**随位姿变**的，臂伸得越远越大，超过碰撞阈值就硬停掉电抱闸。见下面「抱死」一节 |
| 碰撞硬停 / 抱死 | 等约 40 秒再重连，`rtControlling` 会熬过重启 |

```bash
    --arm-backend movel --hz 100 --movel-dispatch-hz 20 --seconds 15
kill %1
```

⚠ `--auto-arm` 跳过键盘离合，**只允许配 `--mock`**。

`--mock` 以前碰到 `--arm-backend movel` 直接退回 `rt`，于是**主循环里 movel
那一整段离线从没执行过** —— 和「MockArm 没有 `_kinematics`，IK 注入那段从没在
mock 里跑过」是同一类盲区（那次代价是一个 `else` 把求解器覆盖掉、横幅照常打印）。
现在换成 `mock_movel.py` 里的内存假控制器，**验的是控制流**（前导闸门、抽稀、
队列跑空补 `moveStart`、`_target_pose` 同步），**不验运动学**：它不模拟逆解失败、
限位、奇异，也**不模拟加速度受限**（真机短段只跑到 25~33mm/s，这里是理想匀速）。
