## 接线与通信

使用 RS485 接口时，电脑通过 **USB-RS485** 接黄线 A、绿线 B、黑线 GND、红线独立 24 V。
默认 **1000000 baud、8N1、Modbus 从站 1**。手册同时列有 RS485 自定义协议，
如果设备被设成该模式，需要先用厂家上位机设为 Modbus RTU；本程序不会盲写协议切换。
手册 4.2 注明 CAN 通过适配盒，原因时手 USB-CAN 不能替代 USB-RS485。
[厂家产品页](https://www.hkvtech.cn/archives/196/) 的通信协议栏也列为 RS485。
只有 CH340 的 USB 标识无法判断外部收发器是 CAN 还是 RS485，需要核对转换器。

### 保留现有 CAN 路径

代码同时支持已有武汉若比特 USB-CAN 的串口封装。可复现本次只读查询：

```bash
python -m experiments.robot.ar5.jog_hkvr --gripper-port /dev/ttyUSB0 \
  --gripper-transport can
```

`--gripper-baud 115200` 是 USB-CAN 的串口速率，**不是 CAN 总线位速率**。
主机发/收 ID 分别用 `--gripper-can-id`、`--gripper-can-rx-id`，接受 `0x` 十六进制。
手册示例表两者写成 1，但第 4.6 节正文要求不同，代码不据此改设备 ID；请以实际设备配置为准。
只读查询失败不能单独区分 ID、速率和物理接口问题。

手册 4.2 写有“CAN（通过适配盒）”，而 4.1 又列出 CAN_H/L 出线定义。
这不足以单独证明当前硬件必须更换适配器；具体出线接口/固件版本仍需硬件或厂家证据。
之前把无回包直接归因于缺少转换盒的结论撤回。USB-RS485 是使用 RS485 接口时的另一条路径。

2026-09-22 进一步排查已经从若比特适配器读回：CAN 1 Mbps、UART 115200，
标准/扩展帧分别启用全接收过滤器；三个控制字节含义也已确认，详见
[CAN 诊断报告](CAN诊断_2026-09-22.md)。
**先读通再运行运动命令**；成功后在下文的跟随/遥操命令里加 `--gripper-transport can` 即可。

## 先测夹爪，不连接 AR5

```bash
conda activate vel-ar5
cd ~/yuhang_workspace/算法/VEL/vel_ar5/openvla-energy

# 只读取目标力，验证通信；不发送运动指令
python -m experiments.robot.ar5.jog_hkvr --gripper-port /dev/ttyUSB0
```

必须先看到“通信已确认”。若无回包，核对转换器、24 V、A/B、设备 ID、波特率和协议。
如参数已更改，用 `--gripper-baud`、`--gripper-id` 指定实际值。

上电后按手册做一次指尖初始化，**夹爪空载执行，会走全行程**：

```bash
python -m experiments.robot.ar5.jog_hkvr --gripper-port /dev/ttyUSB0 --init
```

程序显示的是初始化指令已确认；等夹爪实际走完，再运行下一步。
遥操启动不会自动初始化。

```bash
# 单独让 SO101 扳机带夹爪，AR5 不连接；Ctrl+C 退出
python -m experiments.robot.ar5.jog_hkvr \
  --gripper-port /dev/ttyUSB0 --leader-port /dev/ttyACM0 --follow-leader
```

打印 `target`（扳机指令）与 `actual`（夹爪实测位置）。扳机两端应分别接近 0 和 1，
中间位置应连续变化。标定沿用 `joint_calibration.json` 的 −55.5° / +55.5°。
单独试位置可用 `--opening 0.8`。`--gripper-force 20` 是 1~100 的寄存器值，**不是 20 N**；
速度用 `--gripper-speed`，范围 200~1500。

## 带 AR5 遥操

夹爪单测成功后：

```bash
python -m experiments.robot.ar5.teleop_joint \
  --end-effector hkvr \
  --leader-port /dev/ttyACM0 --gripper-port /dev/ttyUSB0 \
  --no-cameras --relative --scale 0.5 --hz 50
```

启动后机械臂保持当前位置，**Enter 接合/松开机械臂跟随，q 退出**。
夹爪独立跟随扳机，**松开机械臂离合不冻结夹爪**。本命令未加 `--home`，不主动回中心位。
沿用现有机械臂限位和地板保护；新的工具 TCP、含转接板负载/质心仍需实测后填写
`config.py` 的 `ArmConfig`，代码没有用夹爪本体 400 g 代替整套负载。

已有相对模式仍会应用保存的关节缩放；`--scale 0.5` 在这个基础上再减半。
这里使用现有 SO101 关节跟随，不依赖 Vision Pro 或新增本地 IK。

## 数据采集

同一驱动也接到了采集入口，先确认参数再开采：

```bash
python -m experiments.robot.ar5.collect --end-effector hkvr --show-config
python -m experiments.robot.ar5.collect --end-effector hkvr \
  --gripper-port /dev/ttyUSB0 --leader-port /dev/ttyACM0 \
  --out ~/vel_episodes_hkvr
```

`state` 最后一维是夹爪反馈，`action` 最后一维是扳机指令。
夹爪运动有机械延迟，两者不会同步到位。旧的因时手数据和 `--no-hand` 意图数据应分别存放。

## 本次实现与验证

- `drivers/hkvr_protocol.py`：按实际帧长接收、支持分包、CRC 和请求匹配、异常回包报错。
- `drivers/hkvr_hand.py`：独立串口线程，只保留最新目标，目标与实际反馈分开；通信故障锁定报错。
- `teleop_joint`、`teleop`、`collect`：支持 `--end-effector hkvr`；原因时手入口保留。
- 夹爪先连接成功，才启动机械臂；运行时反馈失效，环境请求机械臂停止并退出。
  断线后不会自动重连续跑。退出不会自动松夹；已发给夹爪的运动可能继续到目标位置。

离线验证：17 项新增测试、142 项原有回归通过，20 条手册示例帧逐字节检查通过。
